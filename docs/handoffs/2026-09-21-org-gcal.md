The second machine has none of this set up; the steps below are what #5 says.

Steps, in order, on the **first** machine (done here; kept for reference):

1. `gpg --quick-gen-key "<name> <email>" future-default default never` and `chmod 700 ~/.gnupg`. `future-default` adds the cv25519 encryption subkey; a bare `ed25519` key cannot encrypt and plstore fails with "Unusable public key" (this happened on the first machine and was repaired with `gpg --quick-add-key <id> cv25519 encr never`).
2. Google Cloud console: project, **enable the Calendar API** (org-gcal talks to the REST API `googleapis.com/calendar/v3`; the calendar IDs alone, or the private iCal links, do not grant API access and org-gcal does not consume ICS), OAuth client of type *Desktop app*.
3. Calendar IDs from Google Calendar → Settings → Integrate calendar, for the ten calendars listed in `my/gcal-calendars`. Classroom calendars (`CE*`, `HO*`) and *Aniversários* are deliberately excluded.
4. Write `~/.authinfo.gpg` (visit the `.gpg` path in Emacs; it encrypts on save to the new key). Lines: the forge entry moved from `~/.authinfo`, `machine org-gcal login <client-id> password <client-secret>`, and `machine gcal:<slug> login gcal password <calendar-id>` × 10. Then delete `~/.authinfo` (it is mode 644 and plaintext).
5. Restart Emacs, `, G f` in any org buffer, approve **one browser prompt per calendar** (oauth2-auto keys tokens by calendar ID). The plstore lands in `~/.emacs.d/oauth2-auto.plist`, encrypted to the first secret key in the keyring, so `gpg-agent` caches the passphrase.

6. `~/.gnupg/gpg-agent.conf` with `default-cache-ttl 34560000` / `max-cache-ttl 34560000`, then `gpgconf --reload gpg-agent`; otherwise every sync after ten idle minutes asks for the key passphrase again. On the first machine `~/.authinfo.gpg` ended up symmetric (saved before the encryption subkey existed); re-encrypting it to the key is optional and documented in `config.org`.

On the **second** machine: import the same secret key (`gpg --export-secret-keys --armor <id>` / `gpg --import`), copy `~/.authinfo.gpg` as is, fix `~/.gnupg` permissions, then step 5 again — the plstore is per machine and is not copied.

## Expected on the first fetch

- Each `gcal/<slug>.org` gains level-1 headings appended at the end, within 30 days back / 120 days ahead.
- Every event carries `ORG_GTD: Calendar` and `ORG_GTD_TIMESTAMP` (set by `my/gcal-mark-as-gtd-calendar` on `org-gcal-after-update-entry-functions`), so it shows in the org-gtd Engage day block. `, G c` on an event captures an inbox item linked to it. Events fetched before this hook existed get the properties on their next update only; re-fetching does not touch unchanged events.
- `org-gcal-sync` returns a deferred and does **not** save buffers itself; the `:filter-return` advice does. If a `gcal/` buffer is still modified after a sync, that advice is the first suspect.
- Both machines may sync (fetch is idempotent by `entry-id`, posts are ETag-guarded). The remaining risk is a Syncthing `sync-conflict` file, which the `:before` advice refuses to sync over until resolved by hand.

## Constraints verified in `org-gcal.el` (do not rediscover)

- New events are inserted with `(insert "\n* ")` at `point-max` of the target file; updates locate entries by `entry-id` anywhere in the agenda files. Hence a separate file per calendar and no refiling into `org-gtd-tasks.org` (auto-archive would otherwise write to `org-gtd-tasks.org_archive`).
- The package warns at load time if `org-gcal-client-id`/`-secret` are nil, and registers its OAuth provider right there. Credentials are set in `(after! oauth2-auto ...)`, which fires during org-gcal's own load before that check; do not move them to `:config`.
- `org-gcal-remove-api-cancelled-events` defaults to `'ask`, which prompts in the middle of an async chain; set to `nil` with keyword `KILL`.
- No interactive re-authorisation; delete `oauth2-auto.plist` to start over.
